An experimental programming language

Everything is a {scope}.

Syntact has no functions, no classes, no modules and no type system apart from its values. It has one structure, the scope, and a few operations on it. You derive a scope, collapse it, color a binding with it, or match against it.

Take the tour Syntax at a glance 
square -> {
  n -> 0
  -> n * n
}
5
square{n -> 5}{n -> 5 -> n * n}a new scope; square is unchanged
square{n -> 5}!25collapsed through its production
square!0the original still has its default
Carving {…}

derives a new scope from an existing one, with some bindings given other values.

Collapse !

reduces a scope through its production, the value it yields.

What other languages write as a function call, square(5), is two separate operations in Syntact: derive square with n set to 5, then collapse the result. Most of the language follows from keeping them apart.

01

Scopes and bindings

{…} creates a scope. Inside it, -> binds a name to a value, and . reads a binding back.

point -> {
  x -> 10
  y -> 20
}

point.x   // 10

A scope is an ordered list of bindings. A binding can use whatever is above it, in its own scope or in an enclosing one. Order matters:

x -> 1
y -> x + 1   // fine: x is above

z -> w + 1   // error: w does not exist yet
w -> 1

A file is a scope too, and running a program means collapsing that file. This is a whole program that produces 42:

greeting -> "hello"
answer -> 42
-> answer

Two bindings can share a name

A scope is data, not a symbol table, so two bindings may have the same name. Neither overwrites the other: they are x#0 and x#1. Reading a name gives the last occurrence. Carving targets the first one, unless you name an occurrence.

box -> {
  x -> 1
  y -> x      // built from the first x
  x -> 2
}

box.x            // 2    reading takes the last x
box.y            // 1

box2 -> box{x -> 10}
box2.x           // 2    the last x is untouched
box2.y           // 10   y follows the first x

box{x#1 -> 9}    // carve the second x instead
02

Productions and collapse

A binding with no name on the left is a production: what the scope yields. It replaces return. Collapse, written !, reduces a scope through its production.

add -> {
  a -> 1
  b -> 2
  -> a + b
}

add.a   // 1
add!    // 3

A scope can have several productions. The first is the default and the others are the other things it can produce. This is how sum-like shapes are written:

BoolLike -> {
  -> false
  -> true
}

Expressions resolve, scopes collapse. A binding that holds a scope gives you the scope; ! gives you what it produces. A scope with no production collapses to none.

box -> {
  x -> 1
  y -> {
    -> x + 1
  }
}

box.y    // the scope bound to y
box.y!   // 2

empty -> {
  x -> 1
}
empty!   // none

Productions are lazy

A production runs only when its value is asked for: by !, by a default, by a color that reads the scope, or by a pattern branch that fires. Nothing else runs it.

f -> {
  u8:n
  -> n + 1
}

g -> f{n -> 5}   // a scope: nothing has run yet
g!               // 6, computed here

This is what lets a scope mention itself: a list defined in terms of a list only unfolds as far as a value is actually asked for.

03

Carving

Braces after an existing scope derive a new one. The original is never modified.

Point -> {
  x -> 0
  y -> 0
}

shifted -> Point{x -> 5}

Point.x     // 0
shifted.x   // 5
shifted.y   // 0

Carving runs through everything that depends on the carved binding. This is why it is not argument passing: the whole structure is derived before anything is reduced.

box -> {
  x -> 1
  y -> x + 1
}

box2 -> box{x -> 10}
box2.y   // 11

Arguments without a name fill the bindings in order, skipping productions and holes (chapter 10): Point{3, 4} sets x to 3 and y to 4.

A scope is closed

Carving changes bindings that exist. It never adds one. A misspelled name is an error, so a typo cannot quietly grow a scope.

User -> {
  string:name
  u8:age
}

User{nmae -> "Ada"}   // error: nmae is not a binding of User
04

Defaults and completeness

Every scope is complete. Its bindings have defaults, so it is real data the moment it is written, with nothing waiting to be constructed.

Point -> {
  u8:x
  u8:y
}

Point.x   // 0
Point:p
p.y       // 0

Defaults compose. A structure made of complete parts is complete:

Vec2 -> {
  f32:x
  f32:y
}

Transform -> {
  Vec2:position
  Vec2:scale -> Vec2{x -> 1 y -> 1}
}

Transform.position.x   // 0
Transform.scale.x      // 1

So there is no null and no uninitialized binding. When absence or failure matters, you model it in the structure.

Nothing is ever mutated either. box2 -> box{x -> 10} does not patch box: both scopes exist side by side. When a program needs change over time, it opts in explicitly with resonance or reactivity (chapter 14).

05

Values are sets

There is no separate world of types. 5 is a set with one element. u8 is the name of the set 0..255. A type is simply a set used on the left of :.

u8:age -> 29      // fine
u8:age -> 300     // Constraint_Mismatch: 300 is not in 0..255

Writing u8:age colors the binding age with u8. The compiler must establish that every value age can take belongs to that set. If it cannot, the program does not compile.

The builtin types are names for sets. They are not keywords: they resolve like any name, and you can shadow them.

NameSetDefault

Make your own

Your own types are written with the same operators. There is no difference in kind between u8 and these:

Port -> u16 & >0         // 1..65535
Percent -> u8 & <=100    // 0..100
Digit -> '0'..'9'
WriteMeaning
a | bunion: in a or in b
a & bintersection: in both

Arithmetic works on sets too. u8 + u8 is 0..510, and a comparison whose answer is already decided is that answer: 2 > 2 is false.

A set as a value

As a color, a set admits its elements. To admit the set itself, as one value, write = in front of it:

u8:a -> 5       // 5 is an element of u8
u8:b -> u8      // error: the set u8 is not an element of u8
=u8:c -> u8     // the set u8 itself
=u8:d -> 5      // error: 5 is not the set u8

On a single value = changes nothing: =true and true admit the same thing. Two sets are equal when they have the same elements, however they are written: ~5 | 5 is every integer, so it is int.

Try it

??::u8 is a value the compiler does not know, only that it is a u8. Chapter 09 explains it.

06

Shapes and color

Any scope can be a color. Used on the left of :, a scope is a shape. The same scope is carved with {…} and collapsed with !; the operator chooses the role.

Point -> {
  u8:x
  u8:y
}

Point:p{x -> 10 y -> 20}         // color p by Point, then carve it
Point:q -> {x -> 3  y -> 300}    // Constraint_Mismatch on y

Nobody wrote u8 on the x and y of q. The color of q flows into its fields by itself. This is implicit coloring: a constraint is a property of the structure, not an annotation on one binding.

The name can be left out. Circle: is an anonymous binding shaped like Circle. With productions, that gives sum types:

Shape -> {
  -> Circle:
  -> Square:
}

Color travels with the value. Here every element must be an f32 or a string, though no element says so:

F32OrString -> {
  -> f32:
  -> string:
}

Array{F32OrString}:array -> {0.1 2.0 "hello"}
07

Patterns

? takes a value on the left and branches on the right. The first branch that matches gives the result. A branch with no pattern is the default.

n ? {
  0 -> "zero"
  >0 -> "positive"
  -> "negative"
}

A pattern is any expression that denotes a set, and the branch fires when the value belongs to it. Sets compose, so patterns do too:

value ? {
  (u8 | i8) & >10 -> "a small int above 10"
  -> "something else"
}

shape ? {
  Circle: -> "circle"
  Square: -> "square"
  -> "unknown"
}

One subtlety: a bare u8 is the whole set, while u8: is an anonymous u8 binding, whose complete value is its default 0.

n ? {
  u8 -> "fits in a byte"
  -> "wider"
}

A pattern covers the value

A pattern covers the value it is given, not its color. When the value is known, exactly one branch fires and the others never run. A value that no branch takes is an error: the pattern is not exhaustive.

f -> {
  u8:x -> 5
  -> x ? {=5 -> 1}   // fine: x is 5
}

g -> f{x -> 6}!      // error here: no branch takes 6

To cover a whole color, make the value unknown with ??. Each branch then takes what the branches above it left, and inside a branch the unknown is narrowed to what that branch took:

a -> ??::u8
u8:next -> a ? {
  <255 -> a + 1   // a is 0..254 here, so a + 1 fits in u8
  -> 0
}

Destructuring needs no syntax

A branch's result is written inside its pattern's scope, so the pattern's bindings are simply visible there. Reading them is destructuring.

Circle -> {
  u8:radius
}

area -> {
  Shape:shape
  -> shape ? {
    Circle: -> radius * radius * 3
    -> 0
  }
}

Structural patterns name their pieces with captures. (h) is an alias visible only in the branch. A list pattern mirrors the list's own grammar, so recursion reads naturally:

sum -> {
  Array{u8}:list
  -> list ? {
    {} -> 0
    {u8:(h) ...Array{u8}:(t)} -> h + sum{list -> t}!
  }
}
08

Grammars

A grammar is a set of strings, so a grammar is a type, written with the same operators as every other set. Validation is just coloring.

alpha -> 'a'..'z' | 'A'..'Z'
digit -> '0'..'9'
emailChar -> alpha | digit | '.' | '_' | '-'

Email -> emailChar*1.. + '@' + emailChar*1.. + '.' + alpha*2..

Email:contact -> "team@example.com"   // proven at compile time
Email:oops -> "not-an-email"          // Constraint_Mismatch

'a' is a character and "a" a string. 'a'..'z' is a range of characters, + concatenates, and *1.. repeats one or more times. Complement works as well:

idChar -> 'a'..'z' | 'A'..'Z' | '0'..'9' | '_' | '-'
Identifier -> idChar*1.. & ~(.. + '_')    // no trailing underscore

Identifier:someId -> "someId"   // fine
Identifier:oops -> "bad_"       // rejected
09

Unknowns and proofs

?? is a value the compiler cannot know, such as a program input or a result from outside. ??::u8 says it is a u8.

The compiler keeps the exact form of what depends on an unknown, and a color must hold for every value the unknown can take:

n -> ??::u8
m -> n * 2 - n     // the compiler sees that m is n
u8:ok -> m         // proven for every n
u8:big -> n * 2    // Constraint_Mismatch: n = 128 gives 256

Proofs are colors

There is no separate proof system. Since any value is a set, true is a color like any other, and a property is proven by coloring it true:

true:check -> 2 = 2    // proven
true:oops -> 2 = 3     // Constraint_Mismatch: false is not true

Over an unknown, the same question asks whether a property holds for every value:

decodeEncodeSymmetry -> {
  string:m -> ??
  true:holds -> decode{value -> encode{value -> m}!}! = m
}
10

Holes and genericity

<- declares a hole, a binding the use site fills. Generics are just scopes with holes.

identity -> {
  T <- none
  T:value -> none
  -> value
}

identity{value -> 5}!          // T is inferred: 5
identity{T <- u8 value -> 5}!  // T is filled: u8, and 5 is in u8

A hole is filled by <-, a field by ->, never the other way round. A positional argument never lands in a hole.

A hole that the carve does not fill is inferred from what lands where it is written. What lands is either a value that is sent (it can be read in a wider set without changing its meaning) or a type that is required, such as the color of something the carve provides or an explicit <- (it cannot be widened). The hole takes the one that holds all the others, never their union; then its own color applies.

data -> { u8:x -> 0 }

pair -> {
  u8:e <- 2
  data{e}:first
  data{e}:second
  -> e
}

pair{data{6} data{6}}!          // e is 6
pair{data{6} data{3}}!          // error: neither 6 nor 3 holds the other
pair{e <- 4 data{6} data{6}}!   // error: e requires 4, and 6 is not in 4

A list is a scope with a hole for its element:

List -> {
  T <- none
  -> {}
  -> { T:, ...List{T}: }
}

List{T <- u8}:numbers

The first production is the empty list; the second is a T followed by the rest of the list.

11

Effects and handlers

Everything in Syntact is structural, except effects. An effect is a named event: Log and Audit may carry the same string and still mean different things.

>- emits an event. -< handles it. The nearest visible handler handles it, and execution then resumes where the event was emitted.

Log -> {
  string:message
}

program -> {
  Log -< e {
    -> io.write{e.message}!
  }

  >- Log{message -> "hello"}
  -> 0
}

-> program!

Dependency injection at compile time

Code that needs an allocator, a logger or a clock does not receive one. It emits an event, and the surrounding scope decides what that means.

Alloc -> {
  u64:size
}

Buffer -> {
  u64:size
  ptr -> >- Alloc{size -> size}
  -> ptr
}

WithArena -> {
  Alloc -< e {
    -> arena.alloc{e.size}!
  }
  -> Buffer{size -> 1024}!
}

A library can be specialized by carving its handler, as in FastLib -> SomeLib{Alloc -< e {…}}. Logging, time, randomness, database access and test mocks all work the same way.

12

The external boundary

partly implemented

A program eventually talks to something it cannot reduce: the kernel, a C library. That boundary is a scope whose production points outside.

kernel -> <kernel.so>{
  write -> {
    u8:a  u8:b
    -> ??::u8
  }
}

partial -> kernel.write{b -> 4}   // carved, not executed: pure data
partial!                          // the call happens here, only now

<kernel.so> says where the leaves come from. -> ??::u8 says the result cannot be computed in Syntact but will be a u8. There is no glue code to write, and you can prove things at the frontier:

CString -> (~'\0').. + '\0'   // no interior null, then a terminator

Today the compiler calls real shared libraries with scalar arguments and results. Passing addresses, and so strings and arrays, is still open.

13

Execution patterns

How a collapse runs is decided where it happens, not where the computation is written. No function is declared async, parallel or GPU.

WriteCollapse
work!sequentially
work<!>on another thread
work[!]in parallel on the CPU
work(!)in the background
work|!|on the GPU

They nest: packed(<[!]>) is background, threaded, parallel. The compiler checks that a strategy is legal. A scope that emits unsafe effects cannot be sent to the GPU unless its handlers make that safe.

14

Resonance and reactivity

not implemented yet

Change is opt-in. Resonance is state that changes only through a named event. Reactivity is a value derived from others that follows them when they change.

Counter -> {
  Change -> { u8:value }

  -> {
    u8:value >>- Change -> 0

    Change -< e {
      value -<< e.value
    }

    increment -> {
      >- Change{value -> value + 1}
    }

    -> value
  }
}

>>- declares that value may change, through Change only. -<< performs the update inside the handler. There is no hidden mutable field.

Counter:globalCounter
bool:counterPositive >>= globalCounter.value >= 0

>>= recomputes counterPositive whenever globalCounter.value changes. =<< without a name is a reactive production, such as redrawing a view when its text changes.

15

Files and modules

Files and folders are scopes. @ reads the file system as a graph of scopes, and importing is expansion with ....

Plane2D -> @lib.geometry.Plane

...@lib.geometry                  // import everything

...@lib.geometry{                 // carve a library, then import it
  Plane -> Plane{dimension -> 3}
}

A program is already data before it collapses, so much of what other languages call metaprogramming is ordinary code here:

You pay for what survives

Collapse is a request to reduce everything that can be reduced. Abstractions vanish at compile time, and only the remaining computation is compiled.

A benchmark program from the reference stacks seventeen lines of arithmetic over three runtime inputs. The bootstrap compiler reduces it to 60·a + 78·b + 40·c and emits the same instructions as gcc and clang at -O3. Compared with the equivalent C:

472 Bbinary, vs 15 976 B for gcc -O3
152 µsprocess start, vs 450 µs
5.3 msto a runnable executable, vs 36.9 ms

The gains are structural: no libc, no separate link step, and value ranges known by construction. The arithmetic itself is on par with C.

The twelve rules

The whole core language in twelve lines. When something surprises you, one of these usually explains it.

  1. A scope is an ordered structure, not a symbol table.
  2. A binding is an occurrence, not a variable slot.
  3. A name is a projection, not an identity.
  4. Access resolves a name through the current view.
  5. Carving derives a new scope by targeting existing structural occurrences.
  6. A scope is closed: carving refines existing bindings, it never adds new ones.
  7. Collapse reduces a scope through its production.
  8. Shapes are scopes used as structural constraints.
  9. Patterns are scopes used analytically.
  10. Effects are nominal; everything else is structural.
  11. Defaults compose structurally.
  12. No binding is ever mutated by the core language.

Status

Syntact is experimental and in active development.

What runs today

The bootstrap compiler is written in Odin. It parses, checks colors, reduces, and emits native x86-64 executables, static or linked against shared libraries, with no external linker. A language server provides diagnostics, hover, go-to-definition, rename and completion.

What is still ahead

This site follows the language reference, which describes the design. Events, resonance, reactivity and the full scope algebra are ahead of the implementation, and the type checker is being rewritten as a small algebraic kernel.
